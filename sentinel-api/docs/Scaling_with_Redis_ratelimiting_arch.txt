Arch Query: Can you explain elaborately, step-by-step what you claimed: "Because our keys are cleanly partitioned by tenant and session (rate_limit:tenant:{tenantId}:session:{sessionId}), Redis can process these atomic operations in $O(1)$ time across its single-threaded event loop without key contention. Bucket4j handles this under the hood using atomic Lua scripts or optimized Compare-And-Swap (CAS) operations via Lettuce, ensuring that our Spring Boot application remains completely lock-free and non-blocking."

Arch answer: This is an excellent question. When you are standing in front of a whiteboard during a Staff/Principal engineering interview, throwing around terms like "lock-free" and "$O(1)$" is dangerous unless you can meticulously deconstruct exactly how the metal meets the memory.Here is the step-by-step breakdown of the mechanics keeping the Sentinel architecture resilient at 10,000 concurrent users.Step 1: Clean Key Partitioning (Solving the "Hot Key" Problem)If you track rate limits globally (e.g., rate_limit:global_api_calls), 10,000 concurrent requests will all attempt to read and write to the exact same physical memory address in Redis simultaneously. This is called a Hot Key. Even though Redis is fast, a hot key forces all operations into a single-file line, maxing out the IOPS of a single Redis shard and causing latency spikes.By structuring the key as rate_limit:tenant:{tenantId}:session:{sessionId}, we partition the data into 10,000 unique memory addresses.User A in Session 1 touches Key A.User B in Session 2 touches Key B.They never cross paths. If you ever migrate to a Redis Cluster, the hash slots for these keys will naturally distribute across multiple physical servers, allowing linear horizontal scaling without contention.Step 2: Redis, the Single-Threaded Event Loop, and $O(1)$Redis operates on a single-threaded event loop (multiplexing). It processes one command at a time, sequentially, at lightning speed.Because it is single-threaded, it inherently guarantees that no two commands can mutate the same data at the exact same microsecond.Because Redis is a key-value store built on hash tables, locating a key in memory takes $O(1)$ (constant) time.It does not matter if your Redis instance holds 10 keys or 100 million keys. Finding rate_limit:tenant:ACME:session:999 takes the exact same fraction of a millisecond.Step 3: The Race Condition Threat (Why we need Bucket4j)A Token Bucket algorithm is mathematically more complex than a Fixed Window. To process a request, the system must:READ the bucket state (How many tokens are left? When was the last refill?).CALCULATE the time elapsed and add new tokens if necessary.SUBTRACT 1 token for the current request.WRITE the new state back to Redis.If we wrote this logic in standard Java, we would introduce a massive race condition. If two requests for the same session arrive simultaneously, Thread A and Thread B might both read "5 tokens", both subtract 1, and both write "4 tokens". You just processed two requests but only charged the user for one.Step 4: Bucket4j's Magic (Lua Scripts & CAS)To solve the race condition without using slow, blocking database locks, Bucket4j leverages advanced Redis features—specifically Lua scripting or Compare-And-Swap (CAS) via Lettuce.The Lua Script Approach: Redis allows you to send a small Lua script to the server. Because Redis is single-threaded, it executes the entire script atomically. The Read, Calculate, Subtract, and Write steps happen inside the Redis engine in one uninterrupted block. No other command can interleave.The CAS Approach (Optimistic Locking): Bucket4j reads the token state and notes its "Version." It does the math in Java, then tells Redis: "Write this new token count, but ONLY if the version hasn't changed since I read it." If another request snuck in and changed the version, Redis rejects the write, and Bucket4j instantly retries.Both methods guarantee absolute mathematical precision without ever placing a pessimistic lock on the database.Step 5: Lock-Free & Non-Blocking Spring Boot (Lettuce + WebFlux)Finally, we must protect the JVM.In a traditional Spring Web MVC app (Tomcat), a thread makes a database call and sits idle (blocked) waiting for the network response. At 10,000 users, you would need 10,000 OS threads, which would crash the JVM.Because we are using Spring WebFlux and the Lettuce Redis client (which is built on Netty, just like WebFlux), the I/O is 100% non-blocking.When RateLimiterService calls Bucket4j, the Netty thread fires the Lua script/CAS command over the TCP socket to Redis.The Java thread immediately walks away to process other users' WebSockets.When Redis finishes the calculation and sends the boolean result back over the wire, Netty catches the response and resumes the WebFlux pipeline exactly where it left off.There are zero synchronized blocks in our application code, and zero threads sitting in a WAITING state. CPU cycles are exclusively spent pushing bytes or generating AI tokens.
